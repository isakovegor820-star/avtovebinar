## 1. Архитектура и структура кода

### Бэкенд (Express 5 + TypeScript + ESM)
* **Плюсы:**
  - Переход на **Express 5** обеспечивает встроенную обработку ошибок в асинхронных обработчиках (без необходимости использовать устаревшие обертки в большинстве мест, хотя `asyncHandler` из [http.ts](file:///Users/egor/Desktop/АВТОВЕБИНАР/src/lib/http.ts) все еще применяется для обратной совместимости).
  - Чистое структурирование: разделение на публичные маршруты в [routes/public/](file:///Users/egor/Desktop/АВТОВЕБИНАР/src/routes/public) и админские маршруты в [routes/admin.ts](file:///Users/egor/Desktop/АВТОВЕБИНАР/src/routes/admin.ts).
  - Модули в [src/lib/](file:///Users/egor/Desktop/АВТОВЕБИНАР/src/lib) имеют четкие зоны ответственности (отдельно CRM, отдельно почтовик, отдельно планировщик новостей и боты).
* **Минусы / Точки роста:**
  - В файле [src/routes/admin.ts](file:///Users/egor/Desktop/АВТОВЕБИНАР/src/routes/admin.ts) логика рассылки Telegram-сообщений (`runTelegramBroadcastJob`) выполняется прямо в основном процессе Node.js с использованием простого цикла и `setTimeout`. При росте базы лидов это может заблокировать Event Loop или привести к потере состояния рассылки при перезапуске сервера. Рекомендуется использовать фоновые очереди (например, BullMQ) или хотя бы записывать состояние рассылки в БД.

### Фронтенд (Vanilla JS + CSS в `crisis_premium`)
* **Плюсы:**
  - Отказ от тяжелых фреймворков (React/Vue) в пользу чистого HTML и модульного Vanilla JS ([room.js](file:///Users/egor/Desktop/АВТОВЕБИНАР/crisis_premium/js/room.js), [video.js](file:///Users/egor/Desktop/АВТОВЕБИНАР/crisis_premium/js/video.js)) дает моментальную загрузку страниц и высокие показатели Core Web Vitals (LCP, INP), что критично для конверсии лендингов.
  - Наличие CDN-фолбеков для стилей обеспечивает работоспособность интерфейса даже при сбоях внешних ресурсов.
* **Минусы / Точки роста:**
  - Дублирование логики форматирования дат и работы с API между бэкендом и фронтендом. Логика подсчета времени на клиенте зависит от системного времени пользователя (хоть и корректируется через `state.serverTimeOffset`), что может приводить к рассинхронизации отображения чата на сильно сбитых часах пользователей.

## 2. База данных (Prisma + PostgreSQL)

* **Плюсы:**
  - Отличная Prisma-схема ([schema.prisma](file:///Users/egor/Desktop/АВТОВЕБИНАР/prisma/schema.prisma)) с поддержкой каскадных удалений (`onDelete: Cascade`), индексами по ключевым полям поиска и связей.
  - Таблица `AuditLog` позволяет полностью отслеживать действия администраторов (кто, когда и с какого IP изменил статус сделки или добавил менеджера). Хеширование IP через соль в аудит-логе — прекрасное решение с точки зрения соответствия 152-ФЗ / GDPR.
  - Использование **PostgreSQL Advisory Locks** (`pg_try_advisory_lock`) в [src/lib/reminders.ts](file:///Users/egor/Desktop/АВТОВЕБИНАР/src/lib/reminders.ts) гарантирует, что при горизонтальном масштабировании (запуске нескольких контейнеров Node.js) планировщик напоминаний не отправит пользователям дублирующие сообщения.
* **Минусы / Точки роста:**
  - Отсутствие индексов на полях создания записей (`createdAt` в таблице `events` и `questions`). При накоплении миллионов событий аналитические запросы (группировки UTM, воронки конверсии) в [admin.ts](file:///Users/egor/Desktop/АВТОВЕБИНАР/src/routes/admin.ts) начнут существенно замедлять БД.

## 3. Безопасность

* **Плюсы:**
  - Настройка **Helmet** с кастомной CSP в [src/app.ts](file:///Users/egor/Desktop/АВТОВЕБИНАР/src/app.ts) защищает от XSS и Clickjacking.
  - Интеграция `express-rate-limit` на критические формы (регистрация, отправка вопросов, авторизация в панели администратора) предотвращает спам-атаки и brute-force паролей.
  - Хеширование паролей с использованием надежного bcrypt/argon2.
* **Минусы / Уязвимости (КРИТИЧЕСКИЕ):**
  - **Токены в URL (Запрос/Path):** Токены доступа к вебинару генерируются на сервере и передаются клиенту в параметрах строки запроса `?token=...`. Это приводит к утечке токенов в:
    1. Логи веб-сервера (Nginx/контейнер).
    2. Историю браузера пользователя.
    3. Заголовок `Referer` при переходе по любым внешним ссылкам из вебинарной комнаты.
    *Решение:* Полный переход на HttpOnly, Secure, SameSite=Lax куки (`aspb_room_token`), как описано в Задачах.

## 4. Статус выполнения 3-х критических задач

На основе анализа репозитория на текущей ветке `chore/code-hygiene-and-refactor`:

### ❌ ЗАДАЧА 1. Мерж инфраструктуры + commitlint
* **Статус:** **В процессе.**
* **Анализ:** Ветка `chore/code-hygiene-and-refactor` локально активна, но **не смержена в `main`**. Зависимость `commitlint` добавлена в `package.json`, однако полноценная интеграция хуков коммитов через Husky требует окончательного слияния веток и настройки конфигурации в `main`.

### ❌ ЗАДАЧА 2. Токены: убрать из URL, перевести на cookie-only
* **Статус:** **Не выполнена.**
* **Анализ:** В коде [src/routes/public/registration.ts](file:///Users/egor/Desktop/АВТОВЕБИНАР/src/routes/public/registration.ts) и [src/lib/reminders.ts](file:///Users/egor/Desktop/АВТОВЕБИНАР/src/lib/reminders.ts) по-прежнему генерируются ссылки вида `/crisis_premium/webinar.html?token=...`. Фронтенд-скрипт [aspb-api.js] считывает токен из параметров URL и сохраняет в LocalStorage. Требуется провести рефакторинг по удалению параметров токенов из URL, удалению путей `/webinar/timeline/:token`, и перенаправлению запросов на `/session/current` с авторизацией по кукам.

### ❌ ЗАДАЧА 3. Git-LFS: убрать видео из git
* **Статус:** **Не выполнена.**
* **Анализ:** Файл `crisis_premium/assets/webinar.mp4` весом **54 МБ** до сих пор закоммичен прямо в репозиторий Git. Файл `.gitattributes` отсутствует. Это раздувает размер репозитория и замедляет клонирование.
* *Решение:* Создать `.gitattributes` с описанием LFS-фильтров и провести миграцию истории через `git lfs migrate import`.

## 5. Точечные замечания по коду (с номерами строк)

### 1. Риск блокировки лимитов Telegram API
* **Файл:** [src/routes/admin.ts](file:///Users/egor/Desktop/АВТОВЕБИНАР/src/routes/admin.ts#L20)
* **Код:** `const TELEGRAM_BROADCAST_DELAY_MS = 40;`
* **Проблема:** Задержка в 40 мс между отправкой сообщений разным пользователям слишком мала. Официальный лимит Telegram — не более 30 сообщений в секунду (около 33 мс на сообщение), однако при частой отправке на границе лимита бот моментально получит ошибку `429 Flood Wait`.
* **Рекомендация:** Увеличить задержку до 100-200 мс либо использовать пакетную отправку с обработкой кодов ошибок 429.

### 2. Потеря состояния рассылки при сбое сервера
* **Файл:** [src/routes/admin.ts](file:///Users/egor/Desktop/АВТОВЕБИНАР/src/routes/admin.ts#L140-L177)
* **Код:** Функция `runTelegramBroadcastJob` выполняет рассылку в памяти по массиву `chatIds`.
* **Проблема:** Если во время рассылки по 1000+ пользователям сервер перезапустится (из-за деплоя, нехватки памяти или сбоя питания), рассылка прервется. В БД запишется лог о сбое, но понять, кому сообщение дошло, а кому нет, будет невозможно.
* **Рекомендация:** Сохранять задания рассылки в базу данных со статусами `pending`, `processing`, `sent`, `failed` для каждого `chatId`.

### 3. Разрешенные небезопасные CSP-директивы
* **Файл:** [src/app.ts](file:///Users/egor/Desktop/АВТОВЕБИНАР/src/app.ts#L29)
* **Код:** `scriptSrc: ["'self'", "'unsafe-inline'"],`
* **Проблема:** Наличие `'unsafe-inline'` позволяет выполнять любой JS-код, внедренный на страницу (например, через уязвимости в полях ввода, если они отображаются без экранирования).
* **Рекомендация:** Вынести все инлайновые скрипты из HTML-файлов во внешние JS-файлы и убрать `'unsafe-inline'`. Для динамических скриптов использовать генерацию `nonce` (криптографической соли) на бэкенде.

### 4. Неконсистентность обработки ошибок в фоновых задачах
* **Файл:** [src/server.ts](file:///Users/egor/Desktop/АВТОВЕБИНАР/src/server.ts#L20-L29)
* **Код:** Фоновые задачи запускаются методом `startBackgroundTask`, перехватывающим ошибки синхронно.
* **Проблема:** Если функция инициализации бота или планировщика выполняет асинхронные запросы (например, стучится в Telegram API при старте) и падает с ошибкой (Rejected Promise), этот `try-catch` ее не поймает. Ошибка всплывет в `unhandledRejection` и в продакшене уронит весь процесс сервера (строка 53: `process.exit(1)`).
* **Рекомендация:** Убедиться, что функции запуска фоновых задач не возвращают неперехваченные промисы, либо обрабатывать их инициализацию через `await` до старта прослушивания порта сервера.

## 6. Резюме готовности и дорожная карта (Roadmap)

Проект написан профессионально, с соблюдением стандартов разработки (ESM, TS, Prisma, Docker). Однако для полноценного безопасного запуска в продакшн необходимо выполнить следующие шаги:

1. **Шаг 1:** Смержить ветку `chore/code-hygiene-and-refactor` в `main`. Настроить `commitlint` для стандартизации коммитов.
2. **Шаг 2:** Перевести авторизацию вебинарной комнаты с токенов в URL на HttpOnly Cookie. Это устранит главную брешь в безопасности (утечку токенов).
3. **Шаг 3:** Подключить Git-LFS, убрать `webinar.mp4` из Git-истории с помощью `git lfs migrate`, снизив размер репозитория.
4. **Шаг 4:** Провести нагрузочное тестирование планировщика напоминаний и Telegram-рассылки на тестовой базе из 500+ контактов.
