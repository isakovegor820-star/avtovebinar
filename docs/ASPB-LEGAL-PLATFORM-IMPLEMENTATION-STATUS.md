# АСПБ Legal Platform — статус реализации

Дата: 23 августа 2026 года
Текущий этап: поверх принятого ANA-006 контракта локально реализованы tenant/platform analytics projections, moderation cases/corrections/actions, platform governance, CAT-006 browser acceptance и документированный TEN-002 platform-wide rollout. Production-capable S3 direct multipart contour MED-001 реализован provider-neutral, но реальный provider не выбран и не принят на staging. Локальный runtime оставался в `TELEGRAM_NOTIFY_MODE=log`: реальные Telegram/email-отправки, provider credentials, staging acceptance и production rollout не выполнялись.

## Compatibility layer

- Stable organization `org_aspb` and non-login system owner remain the default scope for legacy `WebinarSession` create/read paths.
- Legacy registration, room, replay, CRM, email, Telegram and `/admin` contracts remain available; новые registration rows дополнительно получают trusted tenant/Webinar/User scope. `AdminUser` не копируется в `User` и не получает implicit tenant membership.
- Unversioned analytics writers проходят один centralized legacy adapter и записываются как `schemaVersion=0`/`scopeKind=legacy`; safe log содержит только event type и correlation ID. Новые writers обязаны использовать version 1. Старый application image остаётся совместим с DB defaults, поэтому штатный rollback ANA-006 — только application image/path без down-migration; silent conversion неизвестных event types отсутствует.
- `PLATFORM_ACCOUNTS_ENABLED=off`, `PLATFORM_TENANCY_ENFORCEMENT=off`, `CREATOR_DASHBOARD_ENABLED=off` и `PUBLIC_CATALOG_ENABLED=off` remain safe defaults. Disabled platform/creator/catalog routes return safe `404`; enabling accounts does not enable tenant enforcement for unmigrated legacy domains.
- Passwordless and invitation email links are generated only in worker memory; database stores SHA-256 hashes. `EMAIL_MODE=log` cancels rather than pretending delivery.
- Invitation and User auth outboxes run through the existing durable reminders worker and are visible in protected health/Prometheus metrics.
- Author verification таблицы пусты после legacy backfill; данные появляются только в новом flow и полностью скрываются флагом `PLATFORM_ACCOUNTS_ENABLED=off`.
- Каждая legacy session получает один Webinar своей организации. Для АСПБ это стабильный `webinar_aspb_legacy`; исходные session/recording/registration/token/CRM/delivery строки не переписываются и не удаляются.
- Legacy sessions не получают искусственное schedule: exact timestamps сохранены, `scheduleVersion=1`, nullable `scheduleId`; existing reminder history только versioned. До creator switch старый flow продолжает работать через stable Webinar.
- Private access management остаётся скрыт теми же platform/creator flags. Existing public compatibility-Webinar не получает grants и продолжает старую воронку. Raw invitation token создаётся только в worker memory; API list не возвращает email/HMAC.
- Для additive deploy без включения flow допустим fallback HMAC на `ADMIN_COOKIE_SECRET`; до создания первого grant обязателен отдельный стабильный `WEBINAR_ACCESS_HASH_SECRET`.
- Новые ChatScenario rows не создаются backfill-ом: legacy JSON scenario остаётся источником старой комнаты. Migration нормализует только synthetic identity/type/scope и не публикует новые messages; compatibility trigger позволяет совместимому старому image писать канонические значения. Creator scenario и moderation API/UI скрыты `PLATFORM_ACCOUNTS_ENABLED=off`/`CREATOR_DASHBOARD_ENABLED=off`.
- Catalog не подменяет legacy `/api/register` и партнёрскую воронку. При выключенном `PUBLIC_CATALOG_ENABLED` ссылка каталога скрыта на legacy landing, read/register routes и sitemap дают 404; UNLISTED compatibility-Webinar не попадает в list/sitemap. Новый register принимает public organization slug как locator, но trusted Organization/Webinar/Session всегда получает server-side из eligible catalog graph.
- Media/transcript tables additive и не создают rows для legacy video. Новый upload не переключает `currentMediaAssetId` до READY + explicit activate; старый room/replay gateway остаётся источником до MED-009 switch.
- Production compose сохраняет одновременно новый private media volume и отдельный `LEGACY_MEDIA_PATH`, смонтированный read-only в прежний same-origin каталог. Deploy fail-closed отклоняет отсутствующий, относительный или слишком широкий system path, поэтому legacy replay/HLS/poster не теряются при смене application image.
- `MEDIA_UPLOAD_CSP_ORIGINS` разрешает только явные HTTPS origins для external direct PUT; local same-origin upload не расширяет CSP. Production validation отклоняет paths, credentials, localhost и HTTP, а `MEDIA_LOCAL_ROOT` — relative/public/root paths.

## Известные риски

- Legacy `Lead` остаётся глобальной compatibility identity, но новый CRM API читает только tenant-scoped `CRMContact` и связанные scoped Registration. Глобальные legacy Telegram broadcast recipients не имеют Organization и поэтому намеренно не используются как tenant evidence; новый `CRMDelivery` всегда имеет Organization/Contact/Registration/Webinar/Session scope и получает recipient только из перепроверенной текущей связи.
- Creator/catalog/viewer UI реализованы, но rollout flags остаются выключены. Новый catalog registration не подменяет legacy партнёрскую воронку и не готов к production switch до SMTP, exact-session staging flow и observation одной тестовой организации.
- `MEDIA_STORAGE_PROVIDER=unconfigured`, `STT_PROVIDER=unconfigured` и `AI_ENRICHMENT_PROVIDER=unconfigured` остаются safe production defaults. DEC-05 теперь выбирает local persistent volume без внешней передачи video; `/metrics` измеряет total/available bytes и inodes без раскрытия path, но staging всё ещё должен зафиксировать alert thresholds и пройти backup/restore, container restart и load acceptance. DEC-06 по-прежнему требует договор/DPA/no-training/retention, бюджет, credentials и provider acceptance; test fakes запрещены production guard.
- MED-004/MED-005 нельзя пометить `verified` до staging-фактической передачи 4 ГБ, volume capacity/restart/load и backup-restore acceptance выбранного local contour; локальная codec/failure matrix автоматизирована. TRN-001 ждёт внешний STT acceptance. MED-009 correctness verified через application gateway, но load acceptance ещё не выполнен.
- Ротация effective `WEBINAR_ACCESS_HASH_SECRET` делает ранее созданную email-bound grant-проверку недействительной; secret должен быть отдельным, стабильным и одинаковым на API/worker.
- macOS File Provider периодически воссоздаёт suffix-copy `node_modules 2`; Vitest теперь fail-safe ищет тесты только в tracked `tests/**/*.test.{js,jsx,ts,tsx}`. Зависимый дубль был перемещён в recoverable `/private/tmp/aspb-node-modules-2-quarantine-20260821`; остальные suffix-directories не тронуты как возможные user data.
- После первого reschedule/cancel outbox job нельзя откатывать worker на image до migration `20260820193000`: старый dispatcher не знает новые service-notification types. Схема additive, но application rollback должен оставаться на compatible image.
- Полный production observation одного webinar/reminder/replay/CRM цикла не выполнен локально; rollout flags должны включаться по runbook независимо.
- Tenant Telegram runtime принят только в local `log` mode. Реальные provider message IDs, Telegram retry-after, bot username/token ownership, polling restart и delivery observation требуют staging smoke test на тестовых chats; `TENANT_TELEGRAM_BOTS_ENABLED` до этого остаётся `off`.
- Tenant Telegram flag пока глобальный, поэтому production canary одной Organization не разрешён до принятого tenant allowlist/rollout mechanism. Additive schema остаётся безопасной при выключенном flag.
- В старой migration history остаётся документированный schema drift manual GIN/token/id-status indexes и default `telegram_broadcast_recipients.updated_at`; новые migrations его не удаляют и не маскируют.
- Реальный SMTP delivery и внешний deploy требуют production credentials/approval. До SMTP verify используется честный degraded `EMAIL_MODE=log`.
- GitHub deployment environments содержат обязательные `STAGING_*`/`PRODUCTION_*` SSH secrets. Workflow остаётся fail-closed: staging/production deploy требует exact-SHA gate, свободное место, backup и environment approval; текущий production rollout из этого release-branch не запускается.
- Резервные MFA recovery codes не входят в критерий TEN-008 и пока отсутствуют; потеря authenticator требует контролируемой operator remediation с аудитом.
- Сроки хранения author profile/evidence, private access grants, viewer progress/favorites/notes/preferences, CRM contact/stage/task/scoring/tag/bulk/delivery, chat/question moderation и tenant Telegram binding/consultant/broadcast/event history не утверждены юристом/DPO; матрица честно запрещает автоудаление до решения. CSV на сервере не сохраняется; signed room URL не сохраняется в Telegram jobs/events, raw recipient chat ID изолирован в private transport rows.

## Deploy verdict

Additive package из **68 migrations**, включая verified analytics/moderation foundation, прошёл targeted local/isolated-PostgreSQL gate и подготовлен только для controlled schema deploy с rollout flags `off` и providers `off/unconfigured`; legacy application path не удаляется. Application rollback возвращает совместимый image/path без down-migration. `TENANT_CRM_ENABLED=off` останавливает новую CRM/delivery, `TENANT_TELEGRAM_BOTS_ENABLED=off` — tenant bot API/flow, а `PLATFORM_ACCOUNTS_ENABLED=off`/`CREATOR_DASHBOARD_ENABLED=off` скрывают creator/moderation path. Текущий exact SHA не одобрен для staging/production: CI/staging того же SHA и verified backup ещё отсутствуют. Внешний deploy остаётся `blocked` и из release-branch не выполняется.
