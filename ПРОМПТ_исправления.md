## БЛОК 1. Git-LFS: убрать бинарники из git-истории

**Проблема:** `crisis_premium/assets/webinar.mp4` (54 МБ) хранится как обычный blob в git. `.gitattributes` отсутствует. `.git` весит 57 МБ, из которых 95% — один видеофайл.

### 1.1. Настроить git-lfs

- Установи git-lfs если не установлен (`git lfs install`).
- Создай `.gitattributes` в корне репозитория:
  ```
  *.mp4 filter=lfs diff=lfs merge=lfs -text
  *.png filter=lfs diff=lfs merge=lfs -text
  *.jpg filter=lfs diff=lfs merge=lfs -text
  *.jpeg filter=lfs diff=lfs merge=lfs -text
  *.webm filter=lfs diff=lfs merge=lfs -text
  *.mov filter=lfs diff=lfs merge=lfs -text
  ```
- Добавь `.gitattributes` в коммит.
- Переведи существующие файлы под LFS: `git lfs track "*.mp4"` и т.д., затем `git add .gitattributes` и `git add crisis_premium/assets/`.
- Закоммить: `chore(infra): track binary assets via git-lfs`

### 1.2. Удалить mp4 из git-истории (ОСТОРОЖНО — rewrite history)

> Выполнять ТОЛЬКО если проект допускает force-push. Если нет — пропусти этот шаг и ограничься шагом 1.1.

```bash
git lfs migrate import --include="crisis_premium/assets/webinar.mp4" --everything
```

После миграции:
- Проверь: `git lfs ls-files` — должен показать webinar.mp4.
- Проверь: `du -sh .git` — размер должен значительно уменьшиться.
- Запушь с `--force-with-lease` (согласовав с командой).

## БЛОК 2. Токены доступа: убрать из URL, перевести на cookie-only

**Проблема:** Токены передаются через `?token=` в URL — попадают в логи сервера, Referer-заголовок, историю браузера. HttpOnly cookie `aspb_room_token` уже существует, но используется только как fallback.

**Текущая архитектура (что есть сейчас):**
- `src/lib/tokens.ts`: `createAccessToken()` генерирует 32-byte base64url токен, `hashToken()` — SHA-256
- `src/routes/public.ts`: `setRoomTokenCookie()` ставит httpOnly cookie, НО `buildFrontendUrl()` создаёт URL с `?token=`, `sendRegistrationState()` возвращает `token` в JSON body
- `crisis_premium/aspb-api.js`: клиент читает `?token=` из URL, сохраняет в localStorage, отправляет в URL-path (`/registration/:token`) и в POST-body (`{ token }`)
- Сервер: `findRegistrationForRequest(req, token?)` — приоритет explicit token > cookie fallback

**Целевая архитектура:**
- Токен НИКОГДА не появляется в URL (ни query, ни path)
- Токен передаётся ТОЛЬКО через httpOnly cookie `aspb_room_token`
- Все API-запросы аутентифицируются через cookie (браузер отправляет автоматически)
- Email/Telegram ссылки ведут на страницу БЕЗ токена — cookie подхватывается автоматически

### 2.1. Серверная часть — `src/routes/public.ts`

**Убери токен из URL-билдинга:**
- Функция `buildFrontendUrl(pathname, token)` — убери параметр `token`, генерируй URL без `?token=`.
- Все вызовы `buildFrontendUrl` — убери передачу токена (successUrl, webinarUrl, telegramBotUrl).
- В `sendRegistrationState` — поля `successUrl` и `webinarUrl` должны быть БЕЗ токена.
- В `POST /register` ответе — убери поле `token` из JSON body. Вместо этого cookie уже установлен через `setRoomTokenCookie`.

**Убери токен из URL-path роутов:**
- Удали роуты `GET /webinar/timeline/:token` и `GET /registration/:token`.
- Оставь ТОЛЬКО cookie-based роуты: `GET /webinar/timeline/session/current` и `GET /registration/session/current`.
- Функцию `findRegistrationForRequest` упрости: всегда читай только из `req.cookies?.aspb_room_token`, убери параметр `token`.

**Убери токен из POST-body:**
- Эндпоинты `POST /events`, `POST /telegram-click`, `POST /questions`, `POST /partner-application` — убери чтение токена из `req.body.data.token`. Вместо этого читай из `req.cookies?.aspb_room_token`.
- Валидацию Zod-схем для этих эндпоинтов — убери поле `token` из обязательных.

**Обнови админские Telegram-ссылки (admin.ts):**
- В обработчике ручной Telegram-рассылки (строки ~1420-1447) — убери `roomUrl.searchParams.set('token', accessToken)`. Cookie уже будет установлена при переходе пользователя по ссылке, если он был зарегистрирован.
- Если нужен одноразовый токен для Telegram (пользователь не залогинен в браузере) — вместо URL-параметра используй короткоживущий one-time код, который пользователь вводит на странице. Но для MVP достаточно просто cookie.

### 2.2. Клиентская часть — `crisis_premium/aspb-api.js`

**Полностью убери работу с токеном из JS:**
- Убери чтение `?token=` из `window.location.search`.
- Убери переменную `token` и всю связанную логику.
- Убери `storage.set('crisisPremiumToken', ...)` и `storage.get('crisisPremiumToken')`.
- Функции `registrationStatePath()` и `timelinePath()` — всегда возвращай cookie-only пути: `/registration/session/current` и `/webinar/timeline/session/current`.
- POST-запросы — убери `token` из body. Сервер будет читать из cookie.
- После успешной регистрации (`POST /register`) — НЕ сохраняй `result.token` (его больше нет в ответе). Просто делай `window.location.href = result.successUrl` — cookie уже стоит.
- `credentials` в fetch-запросах должен быть `'same-origin'` (или `'include'` для cross-origin) — чтобы cookie отправлялись.

**Убери localStorage для токенов:**
- Можно оставить `storage` helper для других нужд (например, UI-предпочтения), но ключ `crisisPremiumToken` — удалить полностью.

### 2.3. Обновить HTML-страницы

- `crisis_premium/success.html` — если есть ссылки с `?token=`, убрать. Ссылка на вебинарную комнату: просто `webinar.html` (без параметров).
- Calendar export (ICS) — URL в описании события: `webinar.html` без токена.

### 2.4. Тесты

- Обнови `tests/core.test.ts` — убери передачу токена через URL-path и POST-body. Все тестовые запросы должны аутентифицироваться через cookie (supertest: `.set('Cookie', 'aspb_room_token=<test_token>')`).
- Обнови `tests/integration.test.ts` аналогично.
- Добавь тест: запрос БЕЗ cookie → 401/403.
- Добавь тест: запрос с невалидной cookie → 401/403.

### 2.5. Обратная совместимость (миграция)

Если продакшен уже работает и у пользователей есть старые ссылки с `?token=`:
- Добавь middleware, который при обнаружении `?token=` в query: (1) ставит cookie `aspb_room_token` из этого токена, (2) делает 302-редирект на тот же URL без query-параметра. Это обеспечит плавную миграцию.
- Этот middleware можно удалить через 2-4 недели после деплоя.

## БЛОК 3. Git-гигиена: Conventional Commits, теги, ветвление

### 3.1. Подключить commitlint

> ВАЖНО: `.husky/` и `lint-staged` существуют ТОЛЬКО в ветке `origin/chore/code-hygiene-and-refactor`, которая НЕ смержена в main. Сначала смержи эту ветку.

```bash
git merge origin/chore/code-hygiene-and-refactor
```

Если есть конфликты — разреши вручную. После мержа убедись что `.husky/pre-commit`, `.eslintrc.cjs`, `.prettierrc.json` на месте.

Затем установи commitlint:
```bash
npm install --save-dev @commitlint/cli @commitlint/config-conventional
```

Создай `commitlint.config.cjs`:
```js
module.exports = { extends: ['@commitlint/config-conventional'] };
```

Добавь `.husky/commit-msg`:
```bash
npx --no -- commitlint --edit ${1}
```

Убедись что `npx husky install` прописан в `package.json` → `scripts.prepare`.

### 3.2. Добавить теги версий

На основе анализа git-истории, привяжи теги к ключевым коммитам:
```bash
git tag -a v0.1.0 -m "Initial platform: registration, CRM, webinar room" 5b4d3a2
git tag -a v0.2.0 -m "Security hardening and production audit" 57a4ba2
git tag -a v0.3.0 -m "Testing, CI, linting infrastructure" 93568e5
git tag -a v0.4.0 -m "UI redesign: flip cards, bento, gradient mesh" <commit_hash_ui_redesign>
git tag -a v0.5.0 -m "Live chat, CSP hardening, ES modules refactor" 250b86e
git tag -a v1.0.0-rc.1 -m "Release candidate: live webinar platform" f36c571
git push --tags
```

(Подставь реальные хеши коммитов из `git log --oneline`.)

### 3.3. Удалить stale-ветку

```bash
git push origin --delete chore/code-hygiene-and-refactor
```

### 3.4. (Опционально) Feature-branch workflow

Для будущих задач создавай ветки по шаблону:
- `feat/<short-description>` — новые функции
- `fix/<short-description>` — баг-фиксы
- `chore/<short-description>` — инфраструктура

Мерж в main — только через Pull Request (с включённым branch protection: require PR, require CI pass).

## БЛОК 4. Дополнительные улучшения (nice-to-have)

### 4.1. Убрать `'unsafe-inline'` из CSP

В `src/app.ts` → `helmet()` → `scriptSrc`:
- Замени `'unsafe-inline'` на nonce-based подход. Генерируй nonce в middleware и передавай в шаблон страницы.
- Для inline-скриптов в `admin.ts` (adminPage) — вынеси JS в отдельный файл `crisis_premium/admin.js`.
- Для `crisis_premium/*.html` — вынеси инлайн-скрипты в отдельные `.js` файлы.

### 4.2. Разбить Docker CMD на init + run

В `Dockerfile` замени:
```dockerfile
CMD ["sh", "-c", "npx prisma migrate deploy && node dist/server.js"]
```
на использование entrypoint-скрипта:
```dockerfile
COPY scripts/docker-entrypoint.sh /app/
RUN chmod +x /app/docker-entrypoint.sh
ENTRYPOINT ["/app/docker-entrypoint.sh"]
CMD ["node", "dist/server.js"]
```

`scripts/docker-entrypoint.sh`:
```bash
#!/bin/sh
set -e
npx prisma migrate deploy
exec "$@"
```

### 4.3. Token revocation

Добавь поле `revokedAt DateTime?` в модель `RegistrationToken` (prisma/schema.prisma). При логауте или компрометации — проставляй `revokedAt = now()`. В `findRegistrationByToken` — проверяй `token.revokedAt === null`.
