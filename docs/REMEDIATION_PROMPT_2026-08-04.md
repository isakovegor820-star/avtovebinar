# Промпт исправления аудита АСПБ

Ты — ведущий инженер по безопасности, backend, frontend и эксплуатации проекта АСПБ. Исправь все подтверждённые замечания аудита ниже. Не ограничивайся косметическими правками: устраняй первопричину, сохраняй совместимость с production и доказывай результат тестом либо воспроизводимой проверкой.

## Главная цель

Сделать регистрацию, согласия, административные операции, напоминания, деплой, резервное копирование и пользовательские интерфейсы безопасными и предсказуемыми. Ни один пункт нельзя объявлять исправленным только по изменению текста или без проверки негативного сценария.

## Жёсткие ограничения

- Не удаляй и не сбрасывай production-данные.
- Не выполняй `prisma db push --accept-data-loss` против неизвестной или внешней БД.
- Учитывай, что production использует нативный PostgreSQL; не подменяй его Docker-БД молча.
- Не раскрывай секреты в логах, тестах, diff или документации.
- Не ослабляй CSRF, CSP, авторизацию, consent-проверки и health-check ради прохождения тестов.
- Сохраняй пользовательские изменения в dirty worktree и не делай commit/stage без отдельного запроса.
- Ошибки сети/5xx не должны выглядеть как лишение доступа, а деградировавшие зависимости не должны считаться полностью здоровым релизом по умолчанию.
- Любая операция, меняющая права владельца, рассылающая сообщения или запускающая deploy, должна быть защищена от гонок и повторного запуска.

## Порядок работы

1. Сначала закрой P1-блокеры безопасности и потери данных.
2. Затем исправь P2 в consent/reminders/admin и инфраструктуре.
3. После этого исправь критические UI/UX и accessibility-дефекты.
4. Для каждого изменения добавь или обнови регрессионную проверку.
5. В конце проверь итоговый diff на обходы защиты, гонки, скрытые fallback и несовпадение production-конфигурации.

## Обязательные исправления

### P1 — безопасность и целостность

- Запрети захват существующего аккаунта через `POST /api/register`: знание email не должно позволять изменить Lead, создать участническую сессию или увидеть PII/Telegram/записи. Для существующего email требуется подтверждённый magic-link/OTP-поток; до подтверждения не изменяй профиль и не выдавай сессию.
- Разбирай consent-поля только как явные boolean-значения. Строка `"false"` обязана стать `false`, а неоднозначные значения — отклоняться валидацией.
- Защити E2E/integration bootstrap от произвольного `DATABASE_URL`. Разрешай destructive setup только для явно тестовой локальной/одноразовой БД; убери безусловный `--accept-data-loss`.
- Привяжи submit-обработчики критических форм синхронно, до любых сетевых `await`, чтобы браузер не выполнял нативный POST без CSRF.
- Не показывай фиктивно синхронизированные слайды. При отсутствии проверенных таймкодов функция должна быть отключена; при наличии — загружай только текущий/следующий слайд.
- Раздели ответы `401/403/404`, timeout/offline и `5xx`: потеря доступа показывается только для подтверждённых access-статусов; для временной ошибки нужен retry без уничтожения клиентского состояния.
- Сделай управление плеером доступным с клавиатуры и screen reader: семантические кнопки, доступные имена, корректный focus, отсутствие глобального перехвата Space в полях/кнопках, управляемый seekbar.
- Обрабатывай fatal/non-fatal ошибки HLS и предоставляй безопасный fallback или понятный retry.
- Деплой должен использовать точный проверенный commit SHA, иметь CI concurrency и серверный `flock`, проверять фактически выбранный compose-файл и не зависеть от неаудированного server-local файла по умолчанию.
- Собирай образ только из содержимого проверенного SHA: незакоммиченные и untracked migration/frontend-файлы на сервере не должны незаметно попадать в Docker context.
- При неуспешном health-check релиз должен автоматически возвращать предыдущую работоспособную версию либо завершаться с явно сохранённым, документированным rollback target.
- После успешного deploy выполняй узкую retention-очистку SHA-tagged образов приложения: сохраняй активный и rollback-релиз, не трогай чужие образы и volumes, поддерживай dry-run. Старые tagged-образы не очищаются обычным `docker image prune` и не должны бесконечно заполнять диск.

### P2 — backend и эксплуатация

- Telegram follow-up отправляй только при активном `marketingTelegramConsent`, без `revokedAt`; повторно проверяй consent непосредственно перед отправкой.
- Сериализуй создание broadcast-задачи транзакцией/advisory lock и не допускай двух активных задач.
- Не позволяй деактивировать/понизить последнего активного owner; проверка и изменение должны быть в одной транзакции.
- При анонимизации отзывай регистрационные токены/сессии и отменяй ожидающие email-задачи, не оставляя PII в snapshot/payload.
- Ручная и retention-анонимизация должны использовать один полный transaction-safe путь: advisory lock по Lead, повторная проверка eligibility после lock и очистка всех связанных PII. Stale snapshot не должен стирать вновь активировавшегося пользователя.
- Тот же Lead advisory lock обязателен для каждого пути, который создаёт токен, outbox-задачу, consent, Event, Question, PartnerApplication, ChatMessage, Telegram binding или заметку. После получения lock повторно прочитай `registration.status` и tombstone Lead; запрос, начатый до erasure, не должен восстановить данные после commit анонимизации.
- Broadcast snapshot создавай только после блокировки всех вошедших в него Lead и повторного preview. Read/modify/write общей JSON-копии job при параллельной анонимизации разных Lead сериализуй отдельным per-job lock, чтобы одна очистка не воскресила данные другой.
- Замени хрупкий `claim -> send` напоминаний на восстанавливаемую аренду/очередь: зависшая задача должна возвращаться в обработку после lease timeout, а повтор не должен создавать неконтролируемые дубли.
- Защити Email/Telegram workers fencing-token'ом: после истечения lease старый worker не имеет права менять задачу или получателя, уже захваченных новым worker.
- Сделай worker самовосстанавливаемым при устойчивой внутренней неисправности; Docker health status без restart-политики процесса недостаточен.
- Сделай backup атомарным: взаимное исключение, временный файл, проверка dump, атомарное переименование, cleanup и явный compose env-file.
- Health-check deploy принимает только HTTP 200 по умолчанию; degraded 503 допускается лишь явным флагом оператора.
- Integration-тесты должны проверять реальные migrations, а не маскировать их через `db push`.

### UI/UX и accessibility

- Убери фиксированную высоту и вложенный scroll у мобильного webinar gate.
- Согласуй оффер страницы регистрации с лендингом.
- Вынеси inline-стили legal-страниц в разрешённый CSP stylesheet.
- Сделай admin login настоящей формой с label, submit по Enter и `aria-live` для статуса.
- Добавь label/описания и live-status партнёрской форме; чат представь как доступный live log.
- Не запускай countdown/reload для уже live/replay-комнаты; CTA вопроса ведёт к чату. Access overlay делает перекрытые controls `inert`, асинхронная ошибка получает alert/focus, ошибка вопроса остаётся в стабильном live-region, а flip-карточки работают Enter/Space и не переворачиваются автоматически.
- Оптимизируй hero asset (современный формат, размеры, responsive source) без визуальной регрессии.
- Удали или перенаправь устаревший корневой prototype, чтобы он не расходился с рабочим интерфейсом.

## Критерии готовности

- Повторная регистрация с известным email без подтверждения не меняет запись Lead и не выдаёт участническую сессию.
- `"false"` не записывается как согласие; невалидные consent-значения возвращают 4xx.
- Destructive test setup отказывается работать с production-like URL и проходит с явно тестовой локальной БД.
- Два конкурентных broadcast-запроса не создают две активные задачи; последнего owner нельзя заблокировать.
- Отозванный Telegram consent исключает отправку даже при гонке между claim и send.
- Запрос, ожидавший Lead lock во время анонимизации, после разблокировки не создаёт новый токен, связанную PII-запись, outbox job, broadcast snapshot или audit с удалённым free text.
- Ошибки API корректно различаются в интерфейсе; retry действительно повторяет запрос.
- Основные формы и плеер работают мышью, Enter/Space и с видимым focus.
- Деплой одного SHA нельзя незаметно заменить содержимым другой ветки; параллельные deploy не пересекаются.
- Untracked migration в server worktree блокирует deploy либо исключён чистым exact-SHA build context; повторные релизы не накапливают неограниченно tagged Docker-образы приложения.
- Повреждённый/неполный backup не публикуется под финальным именем.
- Доступные unit/integration/e2e/static проверки проходят. Если среда блокирует проверку, зафиксируй точную команду, причину и остаточный риск — не называй такой пункт проверенным.
